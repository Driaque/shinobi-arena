# Tournament lifecycle and rewards

Tournaments use saved player profiles and the existing online duel server. A player creates and joins a 2/4/8-seat event; other profiles sign up. The organizer starts a full event, generating shuffled single-elimination pairings. Each entrant selects their normal loadout, opens their bracket and checks in. The server authenticates the profile, validates gear ownership, reserves a pairing match ID and places it in a queue isolated by that exact match ID. Casual/ranked matchmaking cannot fill a tournament seat.

Match results contain trusted tournament/pair IDs from the server context. Inside the same serialized database transaction as match archival, the store compares match ID, participant IDs and pending pairing state, then advances the winner. Completing a round generates the next one. Completing the final inserts one immutable reward-ledger row per entrant, protected by a composite primary key. Duplicate match results exit before changing games, bracket state or awards. Tournament matches never affect Elo or ranked meta statistics.

Reward eligibility uses accepted server simulation ticks, not client time or client-provided results. Twenty seconds of aggregate tournament battle time qualifies. Three completed reward opportunities per profile per UTC day are recorded. Champion/finalist variants reuse the exact standard Katana/Smoke Bomb move IDs, preserving combat balance. The server checks profile unlocks at every online join; offline previews do not grant ownership. Profile recovery codes restore points/unlocks because rewards are keyed by stable profile ID.

Signup mutations and pair preparation use the store's serialized transaction mechanism (PostgreSQL advisory transaction lock or SQLite transaction queue). HTTP withdrawals and tournament socket joins are additionally serialized in the service process so a pending withdrawal cannot race a new local pairing. In-progress matches must use the existing Leave Match forfeit. A pending withdrawal advances the opponent without adding battle-time eligibility. A disconnected/countdown participant forfeits the pairing, but zero-play entrants earn nothing.

Server startup reopens waiting pairings with a fresh match ID; late records for old IDs cannot advance the bracket. Matches restart after interruption, not mid-fight resume. The current deployment is a single authoritative server; cross-instance queue coordination is outside this version. A host should arrange a time and collect signups; there are no scheduled starts or automatic no-show decisions. Registration expires in seven days, with five new events per organizer per UTC day and fifty active events globally. Public lists prioritize active events, followed by recent finished events.

Tests cover registration concurrency, owner checks, capacities, exact opponents, advancement, interrupted/stale/duplicate results, reward caps, expiry, gear validation and restart persistence. Browser validation uses independent desktop/mobile profiles, actual HTTP/WebSocket check-in, a server-simulated battle, forfeit progression, profile rewards, rejected unowned gear and database restart. No production testing endpoint or client result submission endpoint exists.
